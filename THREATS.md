# TrustVault threat register

This register covers the implemented TrustVault system and the final attacker review. Each entry names the attack, mitigation, covering test, and honest current status. Schema-text tests do not substitute for testing effective PostgreSQL privileges or trigger behavior against a running server.

| # | Attack | Mitigation | Covering test name | Status |
|---|---|---|---|---|
| 1 | Public schema privileges allow arbitrary reads or writes to tables by default | The migration revokes all table/sequence privileges from `PUBLIC` before granting specific app-role access | `rejects public schema privileges on the migration` | mitigated: migration assertions exist, but live PostgreSQL grants are not integration-tested |
| 2 | Broad application DB privileges allow row mutation where least privilege is required | The app role grants only `SELECT, INSERT` on the core domain tables | `restricts the application DB role to least-privilege reads and inserts` | mitigated: migration assertions exist, but effective runtime privileges are not integration-tested |
| 3 | A database user can mutate `audit_log` rows to remove evidence | Trigger declarations block `UPDATE`, `DELETE`, and `TRUNCATE` | `blocks update/delete/truncate mutations on audit_log` | mitigated: migration assertions exist, but trigger behavior is not integration-tested |
| 4 | Missing hash-chain fields allow tampered audit rows | `prev_hash` and `row_hash` are required to be exactly 32 bytes | `requires a hash-chain row key in audit_log` | mitigated: schema assertions exist; HMAC generation and verification are exercised by later tests |
| 5 | Audit rows without request correlation are hard to investigate | `request_id` and `outcome` are required and constrained | `requires request correlation and outcome fields for every audit row` | mitigated: schema assertions exist; runtime audit behavior has separate tests |
| 6 | Hash-chain continuity fields are omitted | The schema includes `prev_hash` and `row_hash` | `stores the previous hash in every audit record before hashing the row` | mitigated: migration assertion is shallow; runtime chain behavior is tested separately |
| 7 | App role can mutate audit rows through explicit grants | The app role receives only `SELECT, INSERT` on `audit_log`, and triggers reject row mutation | `keeps the app DB role from mutating audit rows through UPDATE or DELETE grants` | mitigated: migration assertions exist, but effective runtime privileges are not integration-tested |

The PostgreSQL integration tests above ran against the isolated local PostgreSQL 18 cluster. The database engine differs from the PostgreSQL 16 Compose target because Docker was unavailable. The seeded `seed_demo_denied_attempt` row is a clearly labeled demonstration event; the integration test separately exercises and verifies real denied requests.

## Security exception and tradeoff

This phase deliberately uses Fastify 5.12.5+ although the initial stack note specified Fastify 4. npm audit reported an authentication-bypass advisory covering Fastify 4 with no patched 4.x release, so this plan prefers the patched Fastify 5 line. This is an explicit compatibility exception, not a claim that all future Fastify use is automatically secure.
